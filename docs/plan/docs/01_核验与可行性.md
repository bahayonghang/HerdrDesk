# 01 · 核验与可行性

## 0. 执行摘要

**功能等价的 Windows 客户端可以实施，但原调研不宜直接当作开发规格。** 决定性问题不是能否画出侧边栏，而是协议版本、API 订阅入口、终端帧的语义、跨平台进程所有权，以及原代码的复用授权。建议独立建设 HerdDesk，不将 SwiftUI 工程当成可直接跨平台构建的代码基座。

固定对照为 herdr **v0.8.2**（2026-08-19 发布）和 herdrm **v0.5.3**（2026-08-29 发布）。herdr v0.8.2 内嵌 API schema 明确给出 `protocol: 20`、`schema_version: 1`；此前“约 21”的估计不能写入兼容性判断。这里的 20 是已读取的 API schema 声明，不表示本项目将直接实现上游私有二进制终端协议。[E07](../evidence/版本与证据索引.md#e07) [E11](../evidence/版本与证据索引.md#e11) [E12](../evidence/版本与证据索引.md#e12)

**方案实施就绪度暂评 6/10（主观规划评分）**：关键桥接口已有实现，Windows GUI 仍需真机验证；并未给不存在的 Windows 应用计算成熟度。上游仓库整体质量不在本次完整审计范围，不能用这项评分代替其质量评价。

## 2. 对存在争议的判断先给最强反驳

**“原生控件可能其实更合适。”** 正确：如果 raw-stream adapter、IME、焦点与窗口叠加均通过验证，native renderer 能满足纯原生目标。问题不是原生路线错误，而是当前未取得足够证据将其设成发布阻塞依赖。

**“CLI 封装仍然有价值。”** 正确：`api snapshot`、诊断、低频有现成 wrapper 的操作均可继续使用。需要修正的只有“所有 RPC 和事件都能由 `herdr api ...` 转发”这一不成立的前提。

**“Graphics 被忽略并不代表所有图片都绝对不能显示。”** 正确：服务端代码存在帧内 graphics 插入，因此只能确认独立消息路径不完整。最终必须以 bridge + renderer + agent 的完整组合测试判断，不能仅看终端引擎宣传。

**“Windows 远端宿主并非技术上永远不可能。”** 正确：官方 `--remote` 支持范围不等于操作系统理论能力。v1 的排除项是“不实现 Windows 被控宿主适配”，不是宣称任意 Windows SSH 方案不可行。

## 3. 实际核验范围

先读了 README、根目录、`project.yml`、`Cargo.toml` 和 CI，再顺着 `run_api_command → session.snapshot`、`terminal session → ClientMessage → TerminalFrame`、`HerdrService → SocketRPC/SSHTunnel` 下钻。跨文件核验揭示了 graphics 消息和帧内字节的区别；稳定 tag 与默认分支路径不同，v0.8.2 的桥代码在 `src/client/mod.rs`，不能把默认分支 `src/client/terminal_sessions.rs` 行号套过来。[E03](../evidence/版本与证据索引.md#e03) [E04](../evidence/版本与证据索引.md#e04) [E05](../evidence/版本与证据索引.md#e05) [E09](../evidence/版本与证据索引.md#e09)

本环境不能完成 Windows 构建、ConPTY、IME 或 SSH 真机试验，且未完成完整源码 checkout。故本包不提供伪造的全仓 LOC、运行日志、屏幕截图、CVE 数量或已通过的集成测试结论。仓库入口与所有配置并未穷尽审查；未提供或未读取部分，无法作确定评价。
