# 09 · 里程碑、资源与执行 Backlog

## 阶段门禁

采用“先证明协议与输入，再扩大功能”的顺序。阶段可并行准备文档/fixture，但不得在关键门禁失败时靠继续堆UI掩盖阻塞。

| 阶段 | 目标 | 有效人日范围 | 出口门禁 |
|---|---|---|---|
| G0 | 边界验证与设计冻结 | 7–13 | 版本/endpoint明确，Windows桥和最小renderer/IME可行，授权与安全边界无阻塞；失败则收缩为只读或仅远端，不冒充完整复刻。 |
| P1 | 可观测本地控制台 | 9–15 | snapshot/事件最终收敛；Core独立；导航/通知可用；尚不可声称可交互终端。 |
| P2 | 可写本地MVP | 13–22 | 控制、释放、中文输入与三类agent文本TUI通过；GUI关闭不杀任务。 |
| P3 | 多设备MVP | 10–18 | 多设备不串写；SSH身份/配置与断线恢复通过；只承诺已测远端平台。 |
| P4 | 文件与附件功能版 | 11–19 | 双栏文件、冲突/取消/原子写、附件能力表及路径攻击测试通过。 |
| P5 | 发布与质量门禁 | 7–12 | 所有发布AC有真实证据；性能/soak/安全/签名/回滚通过，无已确认P0/P1阻塞。 |

| 阶段 | 动作 | 预期可量化结果（目标，不是已测收益） | 主要回归风险 | 回滚方式 |

### Quick Wins（单项小于1人日）

冻结来源/版本清单、删除虚构CLI示例、区分stable与preview风险、把危险默认行为改为显式产品决策，各可作为HD-001/002/006的0.25–0.5人日子动作。它们已含在WBS里，不额外重复计算。

## 资源估算：不复用“8–12周全功能”的粗略承诺

36项任务合计 **57–99 有效人日**，不含等待授权/证书、硬件采购、重大上游缺陷修复和纯原生renderer替换。建议再留25%集成与不确定性储备，约 **71.2–123.8人日**。这是用于排期的工程估算，不是当前已经完成的工作量。

本地MVP = G0+P1+P2；多设备MVP再加P3；核心功能对等1.0再加P4+P5（不含产品文档列出的1.x扩展）。按一名工程师每周4个有效开发人日计算日历量级；两人也受协议→renderer→IME→真机验收的串行关键路径约束，不能简单把工期除以2。原生renderer若成为强制要求，另加8–20人日候选适配和维护预算，且可能需要上游协作。

建议角色分工：A负责Core/协议/SSH/文件helper；B负责WinUI/renderer/IME/通知/可访问性；两人交叉审查安全边界和资源所有权。没有第二名工程师时保持阶段顺序，不用并行agent产生的代码数量代替验证容量。

## 架构长期演进

1.x 的演进优先级依次为 native renderer可替换性、SFTP provider扩展、更多已验证平台/认证方式、资源预算优化。只有性能数据证明stdio sidecar为瓶颈，才将本地RPC换成进程内pipe实现。上游提供稳定通用bridge后再移除自有RPC bridge；文件面保留独立升级策略。Windows被控宿主或云同步属于新范围，要重新做身份、授权和进程所有权设计。

## Agent/Codex 执行规则

主线程先读取本包README、总规划、对应任务与原始证据，确认任务记录，再分派实现；每次只接受带测试证据的最小增量。任务完成必须检查对应AC，而不是仅检查build成功。禁止为通过测试删掉安全门禁、吞掉错误或把unknown状态改成success。若现有项目使用Trellis，按项目已有规范映射任务，本包不臆造Trellis命令或既存目录状态。
